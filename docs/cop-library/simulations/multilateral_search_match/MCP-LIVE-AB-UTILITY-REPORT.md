## 0. 起点与用户指令

### B · 脆弱维度时窗折扣（`compute/coalition.py :: fragile_time_discount`）
```python
HOLD_REF = 12.0   # 满余量维度(强度1.0)维持≥0.5 的月数
def fragile_time_discount(coal, need, horizon, penalty):
    for 脆弱维 d (最强∈[0.5,0.6)):
        m = max_str - 0.5                       # 脆弱余量
        hold = (m/0.5) * HOLD_REF               # 该维维持≥0.5 的月数
        exposure = 0 if horizon<=hold else min(1,(horizon-hold)/HOLD_REF)
        discount += penalty * exposure
    return min(0.9, discount)
```
- **脆弱维度与时间效用正相关**：余量越小 → 维持月数越短 → 时窗 `H` 超出后效用暴露侵蚀。
- 交付效用 `V' = V·(1−discount)`；夏普利分成同比例缩放（效率公理保持）。

### 时间约束框架（`matcher.py`）
- 默认 `horizon=12` 月；`penalty=0` 时 `V'=V`（**向后兼容，历史模拟可比**）。
- 报告含**无限时窗投影** `V∞ = V·(1−discount(H=2·HOLD_REF))`，直接演示"无时间约束则不保证稳健"。

## 4. 验证用户三点判断

### 判断 1（有限时间约束 → 无约束不保证稳健）✅ 直接坐实
- **基线即伪阳性**：V=210、正和=TRUE，却含 **5 个贴边维度**——"TRUE" 不保证稳健。
- **B 的时间侵蚀**：H=12 时交付 V=109.2（已使通联资本 26.2 < BATNA 33）；无限时窗投影 `V∞=105.0` 进一步下探。折扣随时窗单调增长（H=12→0.48，H=24→0.50），证明脆弱维度价值随时间衰减。
- 报告自动打印："无限时窗下投影 V∞=105.0 不再满足近最大化 —— 无时间约束则脆弱维度侵蚀使稳健性不保证"。

### 判断 2（A 强度覆盖：0.5≠0.97 在效用层）✅ 比配与 V 双重生效
- **比配端**：开启 A 后，引擎自动改选**稳健 4 方联盟**（数擎云/联创/通联/知产），而非处处贴边的 3 方——强度增益让强主体胜出。
- **V 端**：同一联盟 V 从基线隐含 210 落到 **169**（强度加权后，渠道 0.55→cov 0.69、模型 0.5→0.625 拉低均值）。
- **置信分级**：A/B/C 三级把"0.50 vs 0.97"的差距显形为 C 级脆弱 vs A 级稳健，NSFL 披露可读。

### 判断 3（B 折扣 + 脆弱维度时间相关）✅ 完全对应
- B 对 3 方脆弱联盟施加折扣 0.48（5 脆弱维 exposure 之和），交付 V 210→109，**正和满意解翻转为 FALSE**。
- 折扣 = `penalty × Σexposure`，`exposure` 由 `max_str` 决定的维持月数 `hold` 与时窗 `H` 共同决定 → **脆弱维度（低 max_str）的折扣随时窗增长最快**，精确对应"脆弱维度与时间效用相关"。

## 5. 关键结论

1. **原始 V 下"正和满意解 TRUE"确为伪阳性**——用户判断正确。它只保证时窗内二值覆盖，不保证能力稳健。
2. **A 与 B 各自独立推翻该伪阳性**：
   - A 从**比配+估值**端纠正（选稳健联盟、强度加权 V）；
   - B 从**交付**端纠正（时窗折扣使脆弱联盟效用缩水至不达标）。
3. **当前 12 候选池中不存在"全维度稳健"联盟**（每联盟 ≥2 贴边维），故修正后三变体 `pos` 均为 FALSE——这是**诚实结论**：候选池不足以支撑稳健正和，需引入 边算科技(算力0.97)/中证合规(合规0.97)/云渠通联(渠道0.96)/数擎云(数据0.96)/模型坊(模型0.93) 等强主体。

## 6. 标定与后续

- **penalty 是治理可调系数**：演示用 0.10 → 5 脆弱维即 48% 折让（偏强）。生产建议下调至 `0.03~0.05`，或将 `Σexposure` 改为均值以免多脆弱维叠加过罚。
- **A 模式"近最大化"阈值**：基线 `vb×0.9=180` 在强度加权下结构性偏低（cov_strength<1 且多主体重叠使 synergy<1，V 难超 180）。建议 A 模式改用**相对阈值**（≤ 最佳可达 V 的 0.9）或下调绝对线。
- **下一步**：
  1. 演示 12 主体换真实工商/企业库（仅改 server `_list_entities`，引擎与客户端零改动）；
  2. 多连接器并联做跨源去重；
  3. **per-party 脆弱归因**：当前折扣按联盟整体均摊，可改为按脆弱维贡献方分摊（谁提供贴边维谁多担折扣）。
