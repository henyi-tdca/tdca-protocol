## 一、为什么需要双轨身份

TDCA 网页用户中的智能体分两类，身份来源不同、制度载荷不同，**界面必须如实区分**：

| 维度 | TDCA 原生智能体 | 非 TDCA 原生智能体 |
|---|---|---|
| 创建者 | 人类用户（用 TDCA 操作系统创建） | 任意（第三方/外部系统/其他智能体创建） |
| 协议加载 | **创建初始即加载 TDCA 协议**（宪法/NSFL/六要素基线） | 未加载（或仅部分兼容） |
| 合规认证 | **前置认证**（创建即通过合规前置检查） | 无（需另行加入 TDCA 流程） |
| 网页访问 | ✅ 完整访问 | ✅ 可访问网页（浏览/只读） |
| 配置权市场参与 | ✅ 原生资格 | ⚠️ **须「加入 TDCA」后**才可参与 |

## 二、生命周期：人创建 → 智能体创建智能体

- **初始**：智能体一律由人类用户创建（用 TDCA 操作系统），创建即完成协议加载 + 合规前置认证 → 成为原生智能体。
- **繁殖**：原生智能体在授权范围内可创建子智能体（智能体创建智能体）。
  - 子智能体继承创建者身份基线（协议加载 + 认证状态），但**创建行为本身须落 NCA 存证**（谁创建、基于何授权、子体能力边界）。
  - 非原生智能体无权创建（无 TDCA 身份根基）。
  - **数量与深度：不限制**——前提是**反函数有解**：创建操作 f（父→子）存在可计算右逆 f⁻（公理 6：f⁻ 右逆 + 复杂度约束），从任意子体可还原父体身份与创建授权（可审计还原性）。**反函数有解 → 繁殖自由；反函数无解（不可还原/不可审计）→ 创建拒绝（fail-closed）**。
- **界面含义**：任何智能体在界面上的身份标识须可回溯到**创建链**（人 → 智能体 → …），杜绝「野生智能体」冒充原生。

## 三、配置权市场参与资格（准入门槛）

- **注册即缔约（创始人补充 2026-08-29）**：无论人类还是智能体，**注册 = 缔约**——注册流程须先阅读 TDCA 协议并明确同意（勾选确认），同意后方可注册；注册成立即缔约成立（落缔约 NCA 存证）。
- **人机双版本（创始人补充 2026-08-29）**：**一切制度/规范/管理办法均须有人读版与机读版两个版本**（同一制度双版本呈现，同版本号/哈希可溯源）：人读版=自然语言（人类阅读/同意/审批）；机读版=结构化 schema（智能体校验/声明/自动执行）。**注册缔约同样人机双版本**：人类注册=人读版协议+同意勾选；智能体缔约=机读版协议+agent_card 声明+enforce_check 校验；两路缔约均落 NCA（含协议版本/哈希/同意时间戳）。
- **游客态（创始人补充 2026-08-29）**：不注册（未缔约）的人/智能体只能作为**游客**——可访问（浏览门户/文档/资产导航区，沙盒 simulated 演示可体验），但**无任何基础权限**（写操作/存证/创建智能体/缔约/参与配置市场一律无）。
- **原生智能体**：人类用户注册（缔约）后，用 TDCA OS 创建原生智能体（创建即加载协议 + 合规前置认证）——身份继承人类缔约者。
- **非原生智能体**：可访问网页（游客态=只读+社区受限），**参与配置权市场前须完成「加入 TDCA」缔约注册**——复用 agent_card 准入机制（TDCA-HANDOFF-COMMUNITY-RULE-001）：调用方随 dispatch 提供 agent_card（含披露三要素/数据性质标注），enforce_check（AgentCard + 公理 6）通过 → fail-open；未加载 TDCA 协议 → fail-closed（零消耗拒绝）。
- **「加入 TDCA」形态（创始人裁决）**：**缔约**——走 OPC/缔约既有路径（缔约者签署准入 NCA，参照 TDCA-OPC-COMMUNITY-001 准入机制），缔约完成后获得配置权市场参与资格；人类注册缔约与非原生智能体缔约统一为「注册即缔约」原则，人机双版本呈现。

## 四、操作界面：人机交互 ≠ 机机交互（硬区分原则）

**原则**：操作界面上，人类操作面与智能体操作面必须物理/逻辑分离，不可混用同一入口与同一身份凭证。

| 交互面 | 入口 | 身份凭证 | 权限语境 |
|---|---|---|---|
| **人机交互面**（Human-UI） | 自然语言入口 / 表单 / 审批台（HUF 人类签名权 ID71） | 人类账号（实名/DID） | 创建智能体、缔约、签批、裁决、人工确认 |
| **机机交互面**（Agent-UI） | agent.json 端点 / MCP 协议 / API（tdca:echo、nca:get、nca:chain、tdca:core） | agent_card（机器可读身份卡） | 调用工具、落 NCA 存证、NSFL 预检、配置市场撮合 |

**界面落点（三栏门户映射）**：
- 人类栏 = 人机交互面：NL 意图路由（查询/创建/签批）、起草表单、HUF 确认、**人类可查看/管理其创建的原生智能体**（创建链视图）。
- 大模型栏 / 小模型栏 = 机机交互面：agent.json 规格、MCP 实测、tdca-lite；**智能体身份标识显式呈现**（原生 badge / 非原生「未加入 TDCA」提示，agent_card 接入点可视化）。
- 两面的**身份凭证不互换**：人类不做 agent_card 调用（人类走账号），智能体不做人类账号登录（智能体走 agent_card）——这是本原则的核心红线。

**内容层衔接**：人机面产出（人类决策/审批）与机机面产出（智能体生成内容）在**立场分离**（律一/律二/律三）与**数据性质标注**（ID92 real/simulated）上继续强制区分，界面文案与 schema 不得混标。

## 五、与既有制度衔接汇总

| 既有制度 | 衔接点 |
|---|---|
| agent_card 准入（COMMUNITY-RULE-001） | 非原生「加入 TDCA」= enforce_check 通过；准入失败 fail-closed |
| 三栏门户（人类/大模型/小模型） | 界面层落点：人类栏=人机面，大模型/小模型栏=机机面 |
| 双通道架构（DATAFLOW-ARCH-001） | 运行层：静态配置 × 动态状态；本草案管**身份与交互面**，两者正交 |
| 立场分离 / ID92 | 人机/机机产出内容继续分离标注，不得混同 |
| 配置权市场（cypress_pool L2） | 参与资格：原生=创建即具备；非原生=加入 TDCA 后 |
| OPC 准入 / 缔约 | 外部主体加入 TDCA 的既有路径，作为「加入」细则候选 |
