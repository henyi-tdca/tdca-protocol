## 〇、用途与触发

**用途**：FROZEN 交付物（协议包/规格/引擎）需要修改时的标准化变更通道——缺陷修复、功能增强、字段调整均须经本流程，禁止对 FROZEN 交付物直接修改（接口熵=0 的变更侧保障）。

**触发条件**（任一）：
- 缺陷修复（如 SIL 模拟发现的引擎状态机补丁）
- 功能增强（新场景/新调用类型）
- 字段/枚举调整（NCA-Lite type 扩展等）
- 兼容性破坏（协议版本号 +1）

**禁止**：对 L0 法律底层/宪法十六条发起 DCD（硬宪法永不 OTA）；人类签名权不可绕过（ID71）。

## 一、DCD 生命周期（六阶段）

```
① 提案 → ② 六要素声明 → ③ 变更明细（类型/影响面/兼容性/回滚）
      → ④ 制度审查（REV-DCD-xxx，tdca-compliance-auditor）
      → ⑤ 人类签批（TDCA-FOUNDER-xxx）→ ⑥ 升版 + NCA 存证 + 归档
```

| 阶段 | 动作 | 产出 | 责任主体 |
|------|------|------|---------|
| ① 提案 | 描述变更背景与目标 | DCD 提案 | 发现者（AI/人类） |
| ② 六要素 | 目标函数/约束矩阵/先验分布/配置权边界/预期分配/审计轨迹 | 六要素声明 | 执行代理 |
| ③ 变更明细 | 变更类型 + 影响面 + 兼容性分级 + 回滚策略 | 变更明细表 | 执行代理 |
| ④ 制度审查 | compliance-auditor 逐条审查（宪法/TERMS/NSFL） | REV-DCD-xxx 报告 | 制度合伙人 |
| ⑤ 人类签批 | 人类裁决（采纳/驳回/修改） | NCA-DCD-xxx Signed | TDCA-FOUNDER-xxx |
| ⑥ 升版归档 | 版本表更新 + NCA 存证 + DCD 归档 | 新版本 + NCA | 执行代理 |

## 二、变更类型与兼容性分级

| 类型 | 说明 | 版本影响 | 审查强度 | 示例 |
|------|------|---------|---------|------|
| **P0 破坏性** | 字段删除/语义变更/协议不兼容 | 主版本号 +1（如 V1.0→V2.0） | 全量审查 + 人类裁决 | NCA-Lite 字段集重定义 |
| **P1 兼容增强** | 新增字段/枚举/场景（向后兼容） | 次版本号 +1（如 V1.0→V1.1） | 全量审查 | type 枚举加 service |
| **P2 缺陷修复** | 逻辑缺陷修正（不改契约） | 修订号 +1（如 V1.0→V1.0.1） | 定向审查 + 回归测试 | CERTIFIED→ACTIVE 状态机补丁 |
| **P3 文档级** | 注释/措辞/格式 | REV 修订（V1.0-REV2） | 抽查 | nca-lite-mapping 措辞 |

## 四、与既有机制衔接

| 机制 | 衔接方式 |
|------|---------|
| REV 审查链 | DCD 变更须过 compliance-auditor（复用 PACK-001 审查链），输出 REV-DCD-xxx |
| NCA 存证 | 每次 DCD 升版生成工程型 NCA（FileEdit/FileCreate），人类签批回填 |
| OTA 管理器 | 软宪法升级走 OTA（TDCA-OTA）；协议包变更走 DCD——二者互不替代 |
| 版本表 | 各 FROZEN 文档版本表追加 DCD 变更行（含 DCD-ID 引用） |
| 回滚 | 统一"回退至上一次通过版本"（Config-Right-Token.Rollback） |

## 五、负空间预检

| 检查项 | 结果 |

| 直接修改 FROZEN 交付物（绕过 DCD） | ❌ 禁止——NSFL BLOCK |
