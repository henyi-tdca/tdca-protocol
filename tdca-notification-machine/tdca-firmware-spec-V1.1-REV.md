## 二、过渡期处置（三段式，全部复用既有机制）

⚠️ 前置事实：旧版固件未对 `L1-active.json` 作 SE 签名；若直接适用「拒载」将致旧版不可启动。故拒载按下述版本条件生效，**不得径行拒载**。

### 2.1 旧版兼容判定（双条件）

加载侧以两个条件判定固件轨道：

1. `L1-active.json` 是否携带 SE 签名（`sign` 字段，形状同基线 §2.3：`alg`＝`SM2`、`value` 非空）；
2. 固件版本是否在既有**固件版本允许列表**（基线 §6.3 门禁）中标注为 **V1.1-REV 适用版**。

### 2.2 分轨处置

| 轨道 | 判定 | L1-active.json 处置 |
|---|---|---|
| **旧版轨**（允许列表标注 HMAC-only） | 版本为旧版 | 沿用既有 HMAC 路径：⛔ **不拒载**；HMAC 校验失败 → **标记降级**（基线 §四后半句原文适用） |
| **新版轨**（允许列表标注 V1.1-REV 适用） | 版本为新版 | 必须 SE 签名：**验签失败即拒载**；并上报 `[SIGNATURE-FAIL]` → 制度负空间审查（非物理熔断） |
| **未知版本** | 不在允许列表 | fail-closed：按既有版本门禁处理（基线 §6.3），不放行 |

### 2.3 版本协商路径

- 复用既有**固件版本允许列表**：列表逐版本标注该版对 `L1-active.json` 的校验级别（HMAC-only ／ SE 强制）；
- 旧版设备经既有 **OTA 路径**（基线 §2.5：新固件哈希经 SE 验证后写入）升级后进入新版轨；
- 声称新版轨但 `L1-active.json` 签名缺失或验签失败 ⟹ 拒载 ＋ `[SIGNATURE-FAIL]` ＋ 制度负空间审查（基线 §2.4／§六 口径，非物理熔断）。

### 2.4 拒载生效的版本条件

「验签失败即拒载」**仅对允许列表中标注为 V1.1-REV 适用版的固件生效**；对旧版轨固件不生效（其无 SE 签名能力，径行拒载将致不可启动）。

## 三、SIL 模拟正反例（模拟态，⛔ 非真实部署）

过渡期规则之可执行演示见同包模拟器与测试：

- 实现：`simulator/l1_active_loader.py` · `load_l1_active()`（分轨加载，含模拟允许列表 `FIRMWARE_L1_LEVELS`）
- 测试：`tests/test_l1_active_transition.py`
  - **正例**（新版轨）：签名缺失 → 拒载并标记 `[SIGNATURE-FAIL]`；签名形状非法 → 拒载；签名合法 → 加载成功；
  - **反例**（旧版轨）：无 SE 签名 → **不拒载**，加载成功；HMAC 校验失败 → **标记降级**而非拒载；
  - 未知版本 → fail-closed 拒载。

⚠️ 全部为 SIL 模拟：签名值与 HMAC 为模拟占位，密码学验签在 SE 侧（模拟）；本规范不构成「已部署／已投产」声称。
